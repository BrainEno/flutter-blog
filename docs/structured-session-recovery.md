# Structured editing session recovery

The recovery store is local infrastructure, **not a publishing path**. It is
connected to a limited local editor but not the publish queue. It only addresses an
existing article by backend namespace, signed-in account, stable server article
ID and explicit content locale. It cannot recover a new article without a
server ID. Its base/body and base/session metadata snapshots are committed in
one SQLite row; local revisions and exact-value comparisons prevent stale local
editors from overwriting or deleting a later snapshot. They are not server
versions and cannot prevent a remote GET/PUT race.

## What is known

At no-wave revision `8a4fd1fb28fbc42d6e9105ee799dbda8d36e3d65`, REST article
writes require the update slug and `publish`, accept an explicit locale and
one versioned `contentBlocks` array, and accept title, summary, optional work
type, tag IDs and category IDs. An empty summary is regenerated by the server.
The article response may provide ID, locale, slug, title, summary, work type,
tags and categories, but callers must verify each value from the actual source
and requested edition. The existing Flutter `BlogModel` is not an exact source
for all those fields: its tag/category mapping can omit malformed entries, it
uses defaults for missing values, and `isDraft` defaults to false when status
is absent. A false `isDraft` therefore cannot establish published status.
The recovery model never infers a missing value or constructs it from a rendered
or flattened body. The current plain editor and plain publish queue are not
suitable for structured writes and remain unchanged.

Session fields can be null (unknown), while empty title/summary/slug and empty
selection lists remain explicit values. Tag values are editor-facing names;
category values are IDs. A known selection records whether it was touched, so
an untouched selection is different from an explicit clear. Publication state
is `draft`, `published`, or unknown; no unknown status is converted to publish.
The stored metadata is recovery input, not a validated wire request: incomplete
text, blank summary, unknown tag resolution, cover handling, changing server
contracts and live authorization all need review before any write.

## Cover and migration

A cover can be unknown, unchanged, explicitly removed, an exact safe URL, or
local JPEG/PNG/WebP bytes. Local bytes are copied into the SQLite snapshot
as base64 in the same atomic transaction, not stored as an ephemeral picker
path. The 8 MiB limit matches the audited API's binary image cap. MIME and
size are checked, and CRC32 detects common accidental byte damage; CRC32 is not
authentication, and image decoding and upload are not verified. Failure
or corrupt/missing bytes aborts recovery rather than silently dropping the
cover. Replacing a session requires an exact local snapshot; a failed write
leaves the previous snapshot intact. Temporary selection state before a caller
successfully saves is not durable.

Schema v15 adds nullable metadata columns to v14 rows. Null means the old
body-only draft never retained metadata; the upgrade does not guess a title,
cover, summary, status or category. Earlier plain and ownerless drafts are not
migrated into structured sessions. A new client can inspect and augment a v14
row while its original base metadata remains unknown. Rolling a v15 database
back to an older app has not been validated and requires a backup/migration
plan. Storage is not newly encrypted, and base64 covers increase database size
and copy/memory cost; no real-device performance or durability run is claimed.

## Authoring read boundary

At no-wave revision `8a4fd1fb28fbc42d6e9105ee799dbda8d36e3d65`, REST
`GET /articles/:slug` reads published work only; it cannot retrieve an author's
server draft. `GET /me/articles?locale=...&limit=100` is authenticated, includes
published and draft editions, filters the requested locale and returns at most
100 records without an offset. The underlying persistence has `getMyArticle`,
but there is no corresponding owner-detail REST route. An article absent from
the window must therefore be reported as unavailable in the window, not as
deleted, non-existent, or published. Older deployments and network failures
also cannot establish absence. The client never substitutes a public detail
read or another locale for this private read.

The authoring reader validates account, article ID and returned locale, keeps
full raw response fields and reports metadata gaps or future top-level fields
explicitly. Unknown or malformed block structures are not flattened. `status`
is unknown when absent or unrecognized, rather than inferred from a boolean;
nullable metadata and untouched taxonomy selections remain distinct. The
returned response is **not** a valid write request. Local recovery and the
remote edition are returned separately, and reads never overwrite local edits.
The caller must fence its own route/edit generation when applying results, and
use the local revision token when subsequently saving or discarding. Local read
failure blocks automatic initialization from a remote response. A successful
read is not a server-side compare-and-swap or concurrency guarantee.

## Local-only session coordinator

`LocalStructuredSession` is a domain component, not a remote-write path. The
“My articles” list now exposes a distinct optional stable article ID through
its domain model; the public `Blog.id` remains the slug. A structured row opens
a limited local-only screen only when owner, live session, stable ID and exact
locale agree. It re-reads the edition with the account fence rather than using
the list's flattened body. Missing identity is refused, never replaced with a
slug or current content language. Existing Markdown editor, router, write guards
and publish queue are unchanged.

The coordinator opens the exact owner/edition and requires an explicit choice
when a local recovery exists. Cancel does not delete it; confirmed discard uses
its exact local CAS token. A stale or failed discard never replaces another
editor's row. Offline, unsupported and incomplete remote responses can still
leave an existing local session recoverable; they never become a blank article.
Base comparisons are advisory, including when represented fields match. Unknown
metadata, an unknown cover, future fields and unobserved changes cannot prove
that the server did not change.

Each accepted edit is an immutable validated structured snapshot. Saves are
serialized, coalescing later edits behind an in-flight write, and retain the
original base; first creation and subsequent updates use the store's atomic
create-or-CAS operations. A storage error retains the latest pending edit in
memory for an explicit retry; a CAS conflict stops writes rather than rebasing
or overwriting another editor. Consumers must surface these states and keep the
session open, not claim a successful save. `flush` reports durability only when
the local operation completed; `close` waits for admitted writes and refuses
unsaved failure unless the caller explicitly acknowledges abandonment. That
acknowledgement never deletes the previously persisted row.

An identity or generation change invalidates the public state immediately.
Writes admitted before the change may complete only in the captured original
backend/account/article/locale namespace, including edits queued behind an
in-flight save; new edits are rejected. A failed write during sign-out remains
pending and `close` refuses silent abandonment. Already delivered snapshots
cannot be revoked: UI consumers must clear their own references on identity
changes. A process kill, database failure or explicitly abandoned in-memory
edit can still lose changes that did not reach SQLite. Existing recovery data
is not encrypted by this component.

## First local-only screen

The first screen can move or explicitly remove a validated block and toggle
bold on the first run of v1 text/list blocks. Actions save only to local
recovery; all other content and fields remain intact, including image alt and
caption, other runs, links and block IDs. It offers no publishing, text entry,
image editing or general formatting controls. The restriction is deliberate:
the validated document rejects empty and other intermediate input, and the
current recovery schema has no durable place for that in-progress text. A
future text editor must preserve such buffers safely across failure and account
changes rather than silently discarding them.

Recovery requires a choice and discard confirmation. A stale discard or local
CAS conflict never overwrites another editor. Failed in-memory edits block an
ordinary back action, with an explicit warning before abandonment. A session
identity change hides the old article and prevents new operations. The author
list itself still requires a network read. The local recovery index described
below is available from that screen even when the list fails. Forced route
disposal, process death or a storage failure can still lose edits that have not
reached SQLite. True device,
screen-reader and deployed-backend validation remain outstanding.

the authenticated author list is still limited per locale and article writes

## Offline local recovery index

The My Articles toolbar exposes a local index independently of the author-list
request. It requires the current UI account and live session identity to match;
a sign-out, account replacement or identity-generation change invalidates the
index and any editor it opened. It queries only the current backend namespace
and account, across the explicitly stored `en`, `zh-CN` and `zh-TW` editions.
It does not read, parse or display bodies or metadata during listing. The UI
shows the stable article ID and edition rather than inventing a title or slug.
Listing uses keyset pagination by local row ID, 25 entries per query; rows inserted
or deleted during browsing may change what a later page contains, and the list
is not a transactional snapshot. Malformed or overlong keys appear unopenable;
they are not deleted. A database error is shown as an error, never an empty list.
SQLite may scan/sort the account's rows for ordering; there is no schema migration
or added index in this increment, and device performance has not been measured.

Selecting an entry opens the existing local session with an explicitly offline
reader: no network request occurs, the server base cannot be compared, and the
user still must choose whether to resume or discard. The initial row is reread
and its local row ID checked; a deleted/recreated row fails closed. Subsequent
edits and discard continue using the complete existing CAS token. Unknown or
corrupt content fails closed and is never repaired or removed by listing. An
index entry's local identity is not authorization or proof of server existence,
and no remote publish, sync, or cross-device protection is introduced. The
index is accessible only while a matching authenticated account is present in
the app; this is not anonymous access to local drafts. Local storage is not
newly encrypted. Text-entry intermediate buffers remain unsupported.

Upstream was checked again at `a04dfe12988007fcde6b190e27b6199807c4abdf`:
the author endpoint remains limited to 100 per locale; this index does not
attempt to infer whether absent remote articles exist. Real devices, screen
readers, production backend and signed builds have not been validated.

## Isolated intermediate text buffer (schema v16)

The isolated store can persist one intermediate plain-text value in the same
row as a validated recovery. Empty text and whitespace remain exact input, not a
valid structured body. Only unformatted paragraph, heading and quote targets are
accepted; runs, links, lists and images cannot be flattened through this API.
The strict body validator is still required to apply the value. Applying or
explicitly discarding uses the exact body, metadata, buffer bytes, row identity
and local revision in one transaction. A failed validation, storage error or
stale token leaves the earlier value in place. Ordinary body load and mutation
refuse rows containing any buffer, including corrupt or unknown data; the
catalog may still list the identity. This component is not wired into the local
editor, so such rows cannot currently be opened there. It is not a publish
payload, a background queue or a remote concurrency check.

A v15 database upgrades without changing existing body or metadata data; old
rows receive a null buffer. Application downgrade and use of an older client on
a v16 database have not been validated and must not be assumed safe: an older
store is unaware of this column. Back up local data before downgrade. Values
that were only in memory when a process is terminated or a write fails are not
durable. The existing account/session identity fence and save coordinator do
not yet manage these buffers; a future UI integration must provide those fences,
explicit recovery and discard, asynchronous edit ordering, and error handling
before exposing text input. Storage remains unencrypted; devices and screen
readers have not been tested.

## Isolated text session coordination

`LocalStructuredTextSession` coordinates one selected existing recovery row and
one unformatted text block. It uses a single backend-scoped store for both the
parent and buffer, checks the selected row incarnation, and always asks its
caller for an explicit recovery decision. A mismatched block, corrupt row,
missing row or identity change cannot start a blank remote-derived session.
This component does not yet connect to the existing editor, create a recovery
from a remote snapshot, or expose input controls. Integrators must close or
flush the other editing session and reopen the latest local revision before
handing ownership between coordinators; stale tokens conflict, not rebase.

The writer serializes and coalesces rapid input, including empty intermediate
text, using the full local buffer CAS. It keeps pending input in memory on
storage failure or conflict. Only storage errors may be retried, and an
ambiguous committed write conflicts on retry. Explicit apply first flushes and
then requires the strict body validator; explicit discard removes only the
buffer. Both require confirmation and compare the exact stored token. A failed
or conflicting finish is treated as uncertain when closing; the caller must
acknowledge possible abandonment rather than silently discard the in-memory
value. Neither operation sends to the backend. An identity-generation change
clears public state immediately, while already admitted work may complete only
under the original account and backend key. Consumers must clear any copies
previously delivered to them. Process termination or storage failure can still
lose input not yet persisted; the database is not newly encrypted.

The v16 schema and older-client downgrade caveat from the previous section are
unchanged. This adds no schema migration or dependency. Real devices, screen
readers, production networking, and rollback remain unverified.

## Exact body-to-text handoff and indexed buffer reopening

A body session may now explicitly hand off one unformatted text block. It
freezes new body edits, drains already admitted writes and creates a local
parent recovery if the body was previously untouched. A failed or conflicting
save leaves the original coordinator responsible for unsaved work; it is not
silently closed. After a successful flush the body coordinator closes before
returning a text coordinator. The latter must reread an unbuffered parent whose
backend, account, article, locale, row incarnation, local revision, raw body
and metadata JSON, versions and timestamp all match the saved handoff token.
An intervening edit or any buffer, even one inserted without a revision bump,
blocks adoption. Local revisions remain local CAS tokens, not server versions.

An offline index can also resolve a selected existing text buffer without
contacting the server. It fences the account and route generation while reading,
verifies the selected row incarnation and supplies the exact parent and raw
buffer as an expected snapshot. The text coordinator rereads this snapshot and
still requires explicit recovery consent. Missing, changed and corrupt data
are not converted into a blank article or overwritten. Callers must provide a
route-bound identity and fence after async navigation; the use case cannot revoke
private values already delivered to another consumer.

This is domain-only infrastructure: no text input screen or catalog flow is
wired to it yet. The previous editor remains unchanged. There is no migration,
new dependency, remote write, publish or queue change. Persisted data is not
newly encrypted; process death can still lose edits that have not reached the
store. Downgrading to an older app is unvalidated. Real devices and screen
readers remain unverified.

## Local unformatted text screen

The local structure editor now offers a separate text screen for paragraph,
heading and quote blocks without explicit inline runs. The old body coordinator
is closed after an exact local handoff; returning from the text screen returns
to the caller rather than reviving the old revision. Reopen the local recovery
to continue editing the body. Structured runs, links, image fields, lists and
other block data are not flattened or edited by this screen. No server write,
queue operation or publication is enabled.

The screen requires an explicit local recovery choice. Typing is persisted as
an intermediate buffer, including an empty value; applying it to the validated
body or discarding the buffer requires a separate confirmation. Back preserves
a successfully saved buffer, and an unsaved failure or conflict requires an
explicit acknowledgement before leaving. A failed save can be retried and
additional input remains in memory until then. A conflict is not retried against
a newer snapshot. Input is bounded by 20,000 UTF-16 units; an over-limit edit is
rejected rather than truncated. Status and actions use the localized catalogs.

The offline catalog checks for an existing buffered recovery before opening a
body session, without reading the network; damaged buffers fail closed. Both
catalog and author entry fence the UI account as well as the live network
identity. Previously delivered values and OS keyboard state cannot be revoked;
the screen clears its controller on invalidation and consumers must not retain
private values. Process termination, externally removing a route, or storage
failure can still lose input that has not reached SQLite. The app does not add
storage encryption, and older-client downgrade remains unvalidated. Flutter
widget tests do not establish real-device, IME, screen-reader, production
backend, or signed-build validation.

## Immutable inline range operations (not connected to the UI)

`StructuredInlineSelection` captures a nonempty UTF-16 range in one v1
paragraph, heading, quote or list item. A caller can deliberately set or remove
one supported mark or validated link over that range without changing text.
Intersected runs split only where their formatting actually changes; their
other marks, links, optional-key presence and order are retained. Adjacent runs
are not merged. A no-op returns the original document without promoting plain
text into inlines. Editing a plain list item necessarily creates the v1
`itemInlines` representation for all items, with untouched items represented
by a single unformatted run. The original list text and item order do not
change.

The selection rejects v0, missing or wrong targets, collapsed/out-of-bounds
ranges, surrogate-pair boundaries, invalid URLs and results exceeding the
existing run or total-document limits. It never normalizes a URL, infers
formatting from text, or repairs an invalid document. It checks an exact JSON
snapshot of the entire immutable document at apply time; a different snapshot
requires a fresh selection. This is intentionally conservative, including for
unrelated changes, and it is **not** a database CAS token, account fence or
server version. Callers must still use the existing identity-fenced local
session and CAS writer. Selection values, source text and the captured document
remain in memory and cannot be revoked after delivery to a caller.

Offsets are UTF-16 units, not grapheme boundaries: a combining sequence can be
split even though a surrogate pair cannot. Any future UI must independently
validate selection behavior across IMEs, grapheme clusters, accessibility,
identity invalidation and concurrent local changes before integrating it. No
text insertion, formatting toolbar, network request, publication, queue change,
schema migration or dependency is added here. Capturing and checking a range
serializes a document bounded by the existing one-million-unit limit, so it is
linear in document size; it is not a per-keystroke UI API. Tests cover exact
run preservation, rejection, stale selections, CAS conflict, identity changes,
storage retry and offline restart. Real devices and screen readers remain
unverified.

at most 1,000 nonempty runs per block or list item, their concatenation must
match the fallback, URL validation rejects unsafe shapes, and v0 rejects
inlines. The local operation does not imply remote conditional-write support.

## Local whole-run formatting screen

The body editor can open a local formatting screen for v1 paragraphs, headings
and quotes. It shows existing runs lazily and lets the author toggle supported
marks or explicitly apply/remove a link on one complete run. A plain v1 block
is presented as one unformatted run and is promoted only when changed. Text,
run boundaries, other marks, links, blocks, image fields and the local baseline
remain intact. Existing list formatting, arbitrary selected ranges, formatted
text insertion and v0 conversion are not exposed by this screen. A boundary
that would split a UTF-16 surrogate pair is rejected rather than repaired.

Each operation captures the exact displayed body and uses the existing
`StructuredInlineSelection` validation before the body coordinator accepts its
serialized CAS write. A late link confirmation against a changed snapshot is
rejected; cancellation does not create a row. Link input is a temporary dialog
value, not a durable text buffer, and the link is not opened. Invalid or
overlength input is not applied. Account invalidation removes private screen
content, clears the dialog controller and drops its selection reference;
previously delivered values and operating-system keyboard state cannot be
revoked. The shared body session remains responsible for save status, retry,
conflict and explicit acknowledgement before abandoning failed edits. Back
returns to that session rather than closing or reopening a stale revision.
Background flush remains best effort; process death can lose an admitted edit
not yet stored or a link still being entered.

This UI adds no schema migration, dependency, network write, publication or
queue change. The list of at most 1,000 runs is rendered lazily, but capturing a
selection still serializes the bounded document, so it is not a per-keystroke
operation. Tests cover local-only entry, formatting and link preservation,
invalid and stale input, account switching, CAS conflict, save failure/retry,
rapid actions, background state, accessibility semantics and localized large
text. Real devices, IMEs, screen readers, downgrade and production backend
remain unverified. Upstream contract rechecked at
`676b519015ea2a2e09cb0b229fdcd52b2f66f46a`.
