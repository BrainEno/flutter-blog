# Structured editing session recovery

The recovery store is local infrastructure, **not a publishing path**. It is
not currently connected to the editor or publish queue. It only addresses an
existing article by backend namespace, signed-in account, stable server article
ID and explicit content locale. It cannot recover a new article without a
server ID. Its base/body and base/session metadata snapshots are committed in
one SQLite row; local revisions and exact-value comparisons prevent stale local
editors from overwriting or deleting a later snapshot. They are not server
versions and cannot prevent a remote GET/PUT race.

## What is known

At no-wave revision `8a4fd1fb28fbc42d6e9105ee799dbda8d36e3d65`, REST article
writes require the update slug and `publish`, accept an explicit locale and
one versioned `contentBlocks` array, and accept title, summary, optional work
type, tag IDs and category IDs. An empty summary is regenerated by the server.
The article response may provide ID, locale, slug, title, summary, work type,
tags and categories, but callers must verify each value from the actual source
and requested edition. The existing Flutter `BlogModel` is not an exact source
for all those fields: its tag/category mapping can omit malformed entries, it
uses defaults for missing values, and `isDraft` defaults to false when status
is absent. A false `isDraft` therefore cannot establish published status.
The recovery model never infers a missing value or constructs it from a rendered
or flattened body. The current plain editor and plain publish queue are not
suitable for structured writes and remain unchanged.

Session fields can be null (unknown), while empty title/summary/slug and empty
selection lists remain explicit values. Tag values are editor-facing names;
category values are IDs. A known selection records whether it was touched, so
an untouched selection is different from an explicit clear. Publication state
is `draft`, `published`, or unknown; no unknown status is converted to publish.
The stored metadata is recovery input, not a validated wire request: incomplete
text, blank summary, unknown tag resolution, cover handling, changing server
contracts and live authorization all need review before any write.

## Cover and migration

A cover can be unknown, unchanged, explicitly removed, an exact safe URL, or
local JPEG/PNG/WebP bytes. Local bytes are copied into the SQLite snapshot
as base64 in the same atomic transaction, not stored as an ephemeral picker
path. The 8 MiB limit matches the audited API's binary image cap. MIME and
size are checked, and CRC32 detects common accidental byte damage; CRC32 is not
authentication, and image decoding and upload are not verified. Failure
or corrupt/missing bytes aborts recovery rather than silently dropping the
cover. Replacing a session requires an exact local snapshot; a failed write
leaves the previous snapshot intact. Temporary selection state before a caller
successfully saves is not durable.

Schema v15 adds nullable metadata columns to v14 rows. Null means the old
body-only draft never retained metadata; the upgrade does not guess a title,
cover, summary, status or category. Earlier plain and ownerless drafts are not
migrated into structured sessions. A new client can inspect and augment a v14
row while its original base metadata remains unknown. Rolling a v15 database
back to an older app has not been validated and requires a backup/migration
plan. Storage is not newly encrypted, and base64 covers increase database size
and copy/memory cost; no real-device performance or durability run is claimed.
