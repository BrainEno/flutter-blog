# 账户邮箱

改邮箱走 no-wave 的 `PUT /me/email`：浏览器与 App 共用同一条凭据路径。它**不是**
邮箱验证流程的一部分——服务端改完只会把地址标记为未验证，默认**不发信**。

## 与服务器的契约

| 接口 | 客户端用法 |
| --- | --- |
| `GET /me` | 提交前的身份预检：拿回 `id` 与当前邮箱，确认账号没被换掉 |
| `PUT /me/email` | 唯一写入口；body `{password, email}`，需要登录 |

- 成功回 `{ok: true, email, emailVerifiedAt: null}`。`email` 是**服务端归一化后**
  真正存下的地址（trim + 小写），界面显示它而不是用户敲的原文。
- `emailVerifiedAt` 为 `null` 只表示「尚未验证」，**不是**使用前提：读文章、写文章、
  发私信都不看这个字段，客户端也不拿它做门禁。
- 同地址是服务端认可的 no-op（保留原验证状态）。客户端在发电请前就识别出来，
  直接说「已是最新」，白白消耗一次密码校验和一次限流额度没有意义。
- 更换地址**不撤销**任何会话：其他设备继续登录，只是看到旧地址直到下次读 `GET /me`。
- 错误码：`EMAIL_TAKEN`（409，地址属于别人）、`UNAUTHENTICATED`（401，密码错或
  会话失效）、`RATE_LIMITED`（429，用户 5 次 / IP 20 次窗口）、`BAD_USER_INPUT`
  （400，格式不合规）。旧部署没有这条路由时是 404/405。

## 客户端行为

- **先本地校验再发请求。** `validateEmailAddress` 与服务端 `normalizeEmail` 逐条对齐
  （≤254 字符、恰一个 `@`、local 1–64 且不以点开头/结尾、不含 `..`、域名 ≥2 个
  label、每 label ≤63）。**故意不比服务端严**，宁可多发一次请求，也不能自创规则
  拒掉合法地址。当前密码同样先过一遍本地规则。
- **凭据只在本页内存里。** 密码只存在控制器和这一次请求里，提交前就把控制器清空；
  失败、成功、切账号都一样。不写日志、不写失败对象（`Failure` 只留稳定 code）。
- **账号围栏全程携带。** 每次写请求带打开页面时的 `expectedUserId` 与
  `expectedSessionGeneration`。请求在途时切换账号或重新登录，结果被丢弃并锁住表单，
  绝不用旧账号的回包去改新账号的界面。
- **提交前预检身份。** 先 `GET /me`（可安全重放的读）确认 `id` 对得上；对不上就报
  「无法确认当前账户」，这一句明确说**本次没有提交**，避免与「结果未知」混淆。
  预检本身失败时请求还没发出去，因此按普通失败呈现（丢 cause），不报成结果未知。
- **写操作不重试。** `PUT /me/email` 一次到底：不自动重试、不跟随重定向，401 也不
  当作「换个 token 再试」——这一条上 401 更可能是密码错。超时、断连、5xx 或无法
  解析的成功回包都可能发生在提交**之后**，界面统一报「结果未知」，并提示稍后打开
  本页核对当前地址，而不是立刻重提。
- **一个账户同时只有一次安全写入。** 改密和改邮箱共用一个单飞锁：一边在途时另一边
  直接拒绝，提示「已有账户安全修改正在处理」，不去排队，也不并行发两个凭据类写。
- **成功后本地一致。** 服务端回包里的地址写回会话存储（离线启动读到的就是新地址，
  不需要联网纠正），同时更新 `AppUserCubit`，个人中心那一行立刻跟着变。写会话存储
  是尽力而为：已经写成功了，本地记不下来不能反过来报成「结果未知」。
- **旧部署说「暂不提供」。** 404/405 提示当前服务器不支持修改邮箱，不伪装成成功，
  也不显示「已更新」。

## 文案与提示

- 界面固定显示「新地址在服务端是未验证状态，本应用不发送验证邮件」，避免用户以为
  会收到确认信、等一封永远不来的邮件。
- 401 的文案刻意模糊：「当前密码可能不正确，或登录已失效」。服务端对未知账户与错密码
  同样回 `UNAUTHENTICATED`，客户端无法也不应把两者分开。
- 地址输入框与密码框都是 `TextFormField`；密码默认遮蔽、可切换显示，关闭自动更正、
  联想和 IME 个性化学习。整页在 320×640 / 2 倍字号下不溢出（`ListView` + 最大宽度
  680 的约束）。

## 验证（`POST /me/email-verification` 与 `POST /auth/verify-email`）

验证**不是**使用前提：读文章、写文章、发私信都不看 `emailVerifiedAt`。它只回答
「这个地址确实属于你」。个人中心的「验证邮箱」页面把这件事说清楚，并给出两条路。

| 接口 | 客户端用法 |
| --- | --- |
| `GET /me` | 打开页面时读一次：当前地址 + `emailVerifiedAt` |
| `POST /me/email-verification` | 「发送验证链接」，成功是 **202**；body 为空对象 |
| `POST /auth/verify-email` | 粘贴邮件里的链接或确认码后，在应用内兑换（`{token}`） |

### 发信

- **202 只代表服务器受理**，不代表邮件已经送达：服务端投递失败也会吞掉错误并照常
  回 202。界面因此只说「服务器已受理」，并提示可能晚一两分钟、可能进了垃圾邮件。
- **`alreadyVerified: true`**：地址已经验证过，本次没有发信。界面不再显示「未验证」
  这条过时事实，而是重新读一次状态。
- **409 `MAIL_DISABLED`**：这套部署没有配置邮件投递。这是**永久**答案，不是故障，
  重试没有意义；界面直接说「暂时无法用邮件验证，不影响继续使用账户」，而不是假装
  邮件在路上。
- **429**：每位用户每小时 5 次、每个 IP 20 次。界面提示稍后再索取，不自动重试。
- **超时/断连/5xx**：邮件**可能已经发出**。界面提示先查邮箱或刷新状态，不要连续点击。
- 与改密、改邮箱共用同一把单飞锁：一边在途时另一边会被告知「已有账户安全修改正在
  处理」。

### 收尾

邮件里的链接指向**网页**前端（`<身份服务地址>/verify-email?token=…`），不是
`nowave://` 深链，所以应用无法接管它。两种完成方式：

1. 在浏览器里点开链接（网页会调用同一个 `auth/verify-email`），回到应用点「刷新状态」。
2. 把链接或其中的确认码粘贴到页面里，在应用内兑换。适合链接在别的设备上打开、或者
   网页打不开的情况。

客户端只接受服务端同款的确认码形状（32 字节 base64url、恰好 43 个字符），从整段粘贴
文本里用 `token=` 或裸码提取；**提取不到就不发请求**，免得白白消耗 IP 的 30 次额度。
确认码是**一次性凭据**：

- 只在内存里存在一次请求的时间，提交后立即清空输入框，不落盘、不写日志、不在界面
  上回显。
- 兑换请求**不带**当前登录的 Bearer（token 自己就是凭据），也不跟随重定向、不重放。
- **401** 表示「无效、已使用或超过一天」，服务端对三者不区分，客户端也不猜。
- 超时或断连后可能已经兑换成功：界面提示先刷新状态，**不要重复提交同一个码**。
- 旧部署没有这条路由时（404/405）明确说「当前服务器不支持邮箱验证」。

### 状态

- 页面只在内存里保存这次读到的状态，不写进 `User`，也不缓存：验证与否不影响任何
  其他界面，多存一份副本只会多一处过期数据。
- `GET /me` 读失败就显示「暂时无法读取状态」并提供重试；此时不显示发信按钮——不知道
  这是谁的地址，就不该替它发信。
- 账号切换或重新登录会让页面失效：清空输入框、禁用按钮，并说明本次没有提交。

## 没有做的事

- **不接管邮件链接。** 链接指向网页前端，没有 `nowave://` 形式，应用无法自动完成，
  因此保留了「刷新状态」和「粘贴确认码」两条显式路径，而不是猜一个深链出来。
- **不要求先验证。** `emailVerifiedAt` 只在提示里出现，不做任何功能的门禁。
- **不缓存验证状态。** 见上，页面关闭即丢弃。
- **不改找回/重置密码。** 那条路径仍然只在网页完成（`auth/forgot-password` 与
  `auth/reset-password` 未接入）。
