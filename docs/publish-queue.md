# 发布队列（#23）

发帖有两种失败：**内容被拒**和**网络没送到**。前者需要人改，后者只需要再试一次。
发布队列只负责后者：用户按下发布后，这一意图先落盘，再重试，直到服务端接受或需要
人处理。

一个条目做两件事之一：**新建文章**（`kind = create`，靠幂等键保证不重复建文）或
**更新一篇已发布文章**（`kind = edit`，靠文章 id 保证不建出第二篇）。两者共用同一
张表、同一套退避与同一套封面去重。

## 状态

| 状态 | 含义 | 谁会离开这里 |
| --- | --- | --- |
| `queued` | 等待会话、网络或退避窗口 | 下一次 drain |
| `uploading` | 有一次发送在途（**持久化**） | 成功、失败，或下次启动的 `recoverInterrupted` |
| `failed` | 停止自动重试 | 用户在队列页「重试」或「移除」 |

`uploading` 故意写进数据库：进程在发送中被杀，下次启动能看到并**用同一个幂等键
重放**，而不是当作没发生过。

## 三条硬规则

1. **不会静默重复建文。** 每个意图在入队时生成一次 `Idempotency-Key`，之后每次
   尝试都带同一个键。服务端按该键重放（no-wave `POST /articles` 支持，长度 ≤300
   且非空），所以「响应丢了但文章已建」只会在下次重放时返回同一篇。更新条目不需要
   键：`PUT` 按文章 id 定位，重放只会重写同一篇（键仍存着，只当本地标识）。
2. **不会串账号、串后端。** 行带 `backend`（由 `API_BASE_URL` 派生，见
   `lib/core/storage/backend_key.dart`）和 `user_id`；drain 只处理当前登录账号的
   行。`sessionFence` 在每次发送前用**当前**会话重建，所以同一账号退出再登录会
   继续排队（那是账号的长期意图），换账号则不会被别人发出去。
3. **一次只发一条。** 发送前先在事务里 `queued → uploading` 抢占；第二个 drain
   拿不到同一行，页面也不能绕过 runner 直接发。

## 重试与退避

| 失败类别 | 处理 |
| --- | --- |
| `network` / `timeout` / `storage` | 重试，1m → 5m → 15m → 60m → 3h |
| `server` / `unknown` | 同上，但最多 5 次，之后 `failed` |
| `auth`（会话过期/退出） | 保持 `queued`，**不消耗**重试次数，等重新登录 |
| `permission` / `validation` | 立即 `failed`，等人处理 |

编辑器的失败分类与这里一致：只有可能被重试修好的失败才入队，表单校验类失败仍
按原来的错误提示呈现。

## 触发时机

- 应用启动（`main.dart` 调用 `PublishQueueService.start()`：先修 `uploading`，
  再 drain）；
- 会话身份变化（登录/退出/切换账号）；
- 应用回到前台（离线设备重新联网的典型时刻）；
- 打开「发布队列」页并下拉刷新，或点「立即发送」；
- 编辑器把一次发布放进队列之后。

**没有**轮询、没有后台任务、没有服务端推送：队列只在上述事件发生时推进。不联网
时 drain 会直接返回，不消耗任何尝试。

## 封面

选图器给的是临时文件，可能在这条记录等待期间被清理，所以入队时把字节复制到应用
目录 `publish_queue/<entry-id>.bin`，MIME 存在行里；成功或移除时删除文件。

### 封面只上传一次

no-wave 的媒体上传**没有幂等键**，所以旧实现里每一次重试都会把同一张封面再传一遍，
在服务端留下一个没人引用的资源。现在队列自己记住结果：

1. 条目没有 `cover_url`、但存着封面字节时，先单独上传封面（`uploadCover`）；
2. 拿到 URL 后**立刻**写回队列行（`recordCoverUrl`），**然后**才请求建文章；
3. 之后的重试、崩溃恢复、手动重试，都直接用这条 `cover_url` 建文章，不再碰
   `uploadBlogImage`。

媒体资源是不可变的（URL 就指向那份字节），所以记下来的 URL 永远有效；顺序也是
刻意的——先写 URL 再建文章，意味着「已上传、未建文章」之间崩溃时，下次 drain 只会
复用，不会重传。文章本身仍然只有一篇（幂等键保证）。

写回是尽力而为：写失败只记一条 debug 日志，发送照常进行（多传一次封面，好过因此
丢掉一篇文章）。

没有封面的条目完全走老路径（`cover_url` 一直是 NULL，不发任何媒体请求）。孤儿
清理仍属于服务端范围，客户端不做定时删除。

已知边界：

- 失败项的「继续编辑」有意重新发布为**一次新的意图**，所以那时会按新内容的封面
  重新上传一次——旧条目的 `cover_url` 属于那篇没发出去的文章。
- 复用假设媒体资产长期有效（服务端把上传的字节重新编码为 WebP 后长期提供）。若某
  次重试时该资产已被服务端清理，文章会带上一个失效的封面 URL；客户端不做可用性
  探测，也不为此重传——重传才能发现的失败不值得每次都多传一次。

## 改内容：失败项的「继续编辑」

停止重试（`failed`）的条目不再只能「重试」或「移除」。队列页给它多一个
**继续编辑**：把标题、正文、标签和封面装回编辑器，改完再发。

- 重新发布是**一次新的意图**：新的幂等键。正文变了，复用旧键只会让服务端重放原来
  那篇文章，而不是发这次修改的内容。
- 原条目在**新意图有了归宿之后**才删除：发布成功，或再次入队。删除是尽力而为的——
  删早了会丢掉唯一一份文字，删晚了只是一个可见、可移除的多余行。
- 只有 `failed` 能继续编辑。`queued` 随时可能被 drain 抢走，`uploading` 已经在路上，
  这两种状态改内容会和正在发送的请求打架。
- 队列里的封面存在应用目录里，没有选图器文件，所以编辑器直接预览字节
  （`Image.memory`），发布时仍按原来的上传路径带上同一份字节。

## 编辑已发布文章

编辑失败（网络/超时/服务端错误，即编辑器认为值得重试的那几类）时，改动不会丢：
条目以 `kind = edit` 入队，`target_id` 记住要更新的文章（公开 id，也就是 slug）。

- **不会建出第二篇。** 重放走 `PUT /articles`（按 id 定位），发两次写的是同一篇。
- **不重传没换过的封面。** 只有这次改了封面才把字节存进队列；重放时先用
  `cover_url`（见上一节），没有 URL 才上传一次。没换封面就没有字节，重放会保留
  服务端现有的封面。
- **失败分类与新建一致。** 内容/权限被拒（例如服务端正文结构无法安全回写）直接
  `failed`，等人处理；会话过期只暂停，不消耗重试次数。
- **失败项的「继续编辑」进入更新模式**：恢复出的编辑器以该文章为目标，保存时是
  更新，不会变成「拿着旧文本再发一篇新文章」。
- **写覆盖是有意的**：队列里的文本就是用户当时确认要写下的内容，重放时覆盖服务端
  当前文本（最后写入者胜）。文章若已被删除，重放会以 `failed` 停下。
- 同一篇文章可以同时有多条编辑条目（用户改了两次两次都失败），它们按时间顺序重放，
  最后一条生效。
- 顺序上先传封面、再发更新：若服务端随后以「正文结构无法安全回写」拒绝，那张封面
  已经上传了（和新建路径一样，后端没有删除端点）。这种条目会停在 `failed` 并显示给
  用户，重试会复用那次的 URL。

## 范围

队列只处理**文章的写入**：新建文章、更新已发布文章。删除、点赞、评论等其它写操作
不在本队列范围内（它们要么已有自己的幂等/串行化，要么不需要离线重试）。

## 与草稿的关系

草稿是「我写了」，队列是「我要发」。编辑器发布前仍先存一份精确草稿快照；一旦
入队成功，本地草稿即被清理，因为队列行已经持有同样的文字与封面。发布期间继续
编辑的内容仍留在草稿里，不会被丢掉。
